# Process HUD

[English](README.md) · **Русский**

**Codex не должен тратить квоту на ожидание процессов.**

Сборка проекта, тесты, импорт данных или загрузка могут выполняться минутами и часами. Сама работа идёт без участия ИИ, но Codex нередко продолжает спрашивать у системы: «Ещё работает? А теперь? А теперь?» Такие проверки расходуют модельные ходы и контекст, хотя ничего не меняют.

**Process HUD передаёт ожидание обычной локальной программе.** Codex регистрирует длительную задачу, получает её идентификатор и заканчивает свой ход. Пока команда выполняется, HUD следит за ней без обращений к модели. Когда процесс завершится — успешно, с ошибкой или прерыванием — подключённый мост сообщит результат в исходный диалог, чтобы Codex мог продолжить работу. Если во время выполнения возникла ситуация, требующая решения, HUD может сообщить и об этом.

Это главная задача проекта. Полупрозрачная панель — удобный способ видеть происходящее самому, не возвращая агента к работе ради очередной проверки.

## Вместо постоянных проверок — событие, которое возвращает Codex к работе

Обычный подход выглядит так:

```text
Codex запускает тесты
  → проверяет, закончились ли они, с повторной обработкой контекста
  → ждёт
  → снова проверяет, с повторной обработкой контекста
  → ждёт
  → снова проверяет, с повторной обработкой контекста
  → наконец читает результат
```

С Process HUD:

```text
Codex запускает тесты через HUD
  → HUD принимает наблюдение за процессом
  → Codex завершает ход и не расходует токены на ожидание
  → HUD самостоятельно отслеживает выполнение
  → готов результат или нужна помощь? HUD отправляет событие
  → Codex возобновляет работу в нужном диалоге
```

HUD не «думает» вместо агента и не вызывает модель каждую секунду. Он проверяет состояние процесса обычными средствами операционной системы. Модель снова нужна лишь тогда, когда появился результат или действительно требуется её решение.

При этом Codex получает не только сообщение об успехе: **ошибка, прерывание и потеря возможности достоверно определить результат тоже обрабатываются**. Неизвестный исход не выдаётся за успешный, а задача не запускается повторно самовольно.

### Почему это важно для квот

В [исследовании JetBrains Benjamin-Plus](https://github.com/JetBrains/benjamin-plus-skill/blob/main/EXPECTED-RESULTS.md) на Java SWE-bench **45,8% шагов агента в одной из изученных конфигураций были проверками состояния**, включая 3 982 опроса с ожиданием менее пяти секунд. Это не означает «45,8% всех токенов»: измерялась доля шагов конкретной конфигурации. Но масштаб бессмысленной работы хорошо виден.

Мы проверили и собственно ожидание через Process HUD. В двух испытаниях — обычного диалога Codex и цепочки «субагент → основной агент» — за **120 секунд ожидания было 0 новых модельных ходов и 0 обновлений счётчиков токенов**. После выполнения результат дошёл до нужного диалога. Отдельно проверялись доставка успешного завершения, ошибки и прерывания.

То есть **наблюдение за длительной задачей можно выполнять вообще без модельных вызовов в период ожидания**. Это не обещание фиксированного процента экономии всей квоты: запуск задачи, обработка результата и последующая работа агента по-прежнему расходуют токены.

## Установить с помощью Codex

**Установить HUD может любой Codex — не обязательно тот, кто будет потом им пользоваться.** Программа и skill устанавливаются **один раз для пользователя Linux** и доступны другим диалогам и экземплярам Codex на той же машине, в том числе в разных проектах. Повторная установка для каждого агента не нужна. Просто передайте одному из них [инструкцию по установке и подключению](docs/INSTALL_FOR_CODEX.md).

Достаточно отправить Codex:

> Прочитай инструкцию по адресу:
> https://github.com/ViskyG/process-hud/blob/main/docs/INSTALL_FOR_CODEX.md
> Установи Process HUD на этой машине, добавь skill и подключи автоматическое продолжение Codex там, где оно поддерживается. Проверь не только запуск, но и возврат после успешного завершения и ошибки. Сообщи, что настроено и что осталось неподтверждённым. Во время ожидания процессов не выполняй собственные циклические проверки.

Codex проверит окружение и уже имеющуюся установку: если HUD и skill на месте, переустанавливать их не требуется. Если репозиторий закрыт и агент не может открыть ссылку, дайте ему доступ к клонированному проекту и путь **`docs/INSTALL_FOR_CODEX.md`** внутри него. Инструкция не требует вручную переносить код в настройки Codex.

## Как Codex работает с HUD

Для агента предусмотрен **skill** — инструкция, которая учит использовать Process HUD по назначению:

- передавать HUD достаточно долгие неинтерактивные команды, а не все подряд;
- после регистрации задачи прекращать собственные циклические проверки и ожидание через `sleep`;
- возвращаться к задаче по событию о завершении, ошибке или необходимости вмешательства;
- читать итоговый отчёт, проверять результат и убирать обработанную запись из панели.

При первом использовании с автоматическим продолжением skill сам проверяет, подключён ли текущий диалог к мосту Codex App Server. Если нет, **агент сам запускает настройку** из установленного HUD, сохраняет резервные копии и проверяет результат. Если мост настраивается впервые, нужно **однократно перезагрузить окно VS Code**: уже запущенный App Server нельзя подменить новым подключением без перезапуска. В последующих диалогах перенастройка не требуется.

**Никаких ручных привязок агента или проекта.** Источник задачи определяется по идентификатору реального диалога Codex. Возврат результата автоматически адресуется ему, а у субагентов — основному агенту.

Например, после успешного подключения моста Codex может запустить:

```bash
process-hud run --title "Тесты проекта" --resume-codex --cwd /путь/к/проекту -- python3 -m pytest
```

У всех Codex одного пользователя общие команда, skill, хранилище задач и панель. Но **ответственность за результат привязана к конкретному диалогу**, который зарегистрировал задачу, а не к установщику HUD. Подключённый мост направляет событие этому диалогу; для субагента — основному агенту. Так ожидание не требует ни постоянно активного диалога, ни отдельного модельного хода для пересылки результата от уже завершившего работу субагента.

**Skill доступен Codex в VS Code и терминальном Codex.** Запуск и наблюдение за задачами возможны в обоих вариантах. Автоматический возврат в диалог требует моста: для Codex в VS Code на Linux x86_64 он настраивается самим skill при первом использовании. Отдельная проверенная интеграция для автоматического возврата в терминальный интерфейс пока не опубликована.

## Если хотите настроить вручную

Нужен **Linux с Python 3.10+** и модулем `venv` (на Ubuntu — пакет `python3-venv`). Интерфейс проверен на Ubuntu 24.04 с GNOME/X11. Из терминала:

```bash
git clone https://github.com/ViskyG/process-hud.git
cd process-hud
bash install.sh
~/.local/bin/process-hud doctor
```

Это одна установка для всех экземпляров Codex в пользовательском окружении. Если HUD уже установлен, достаточно проверить `~/.local/bin/process-hud doctor` и наличие skill; **не запускайте установщик повторно из другого диалога без необходимости**. Мост Codex при первом использовании настроит сам skill. Если вы предпочитаете сделать это вручную:

```bash
~/.local/share/process-hud/venv/bin/python ~/.local/share/process-hud/scripts/install_codex_bridge.py --ensure
```

Если мост установлен впервые, перезагрузите окно VS Code один раз. Настройщик создаёт резервную копию и не изменяет уже правильно настроенное подключение. В настоящем диалоге Codex после перезагрузки используйте `--resume-codex`. [Подробности и отключение моста →](docs/CODEX_BRIDGE.md)

Команды используют стандартные пути установки, необходимые нынешнему настройщику моста. `doctor` выдаёт диагностику, а не подтверждение всей интеграции. Если `process-hud` не находится через `PATH`, используйте `~/.local/bin/process-hud`.

Проверить обычный запуск задачи и работу панели можно так:

```bash
~/.local/bin/process-hud ui show
~/.local/bin/process-hud run --title "Демонстрация" -- \
  ~/.local/share/process-hud/venv/bin/python \
  ~/.local/share/process-hud/examples/demo.py
```

Команда сразу вернёт ID задачи, а HUD покажет её выполнение. **Эта демонстрация проверяет наблюдение, но не автоматическое пробуждение Codex.** Для проверки возврата по событию следуйте [пошаговой инструкции](docs/INSTALL_FOR_CODEX.md#4-проверь-работу).

## Что видит пользователь, пока Codex работает

Пока Codex не тратит модельные вызовы на ожидание, HUD позволяет самому видеть состояние переданных ему задач:

- **Небольшая прозрачная панель поверх окон.** Видно, какие задачи Codex передал HUD, какие ещё выполняются и какие завершились; окно подстраивается под список.
- **Логи и результат по клику.** Можно посмотреть код завершения и последние сообщения программы.
- **Реальный прогресс.** Если задача сообщает число обработанных элементов или проценты, HUD показывает прогресс и оценивает оставшееся время. Если таких данных нет — не придумывает их.
- **Несколько источников задач Codex.** Локальные процессы, подключение к существующему PID, Docker, Kubernetes Job и SSH.
- **Уведомления и звук.** О завершении можно узнать, даже если панель не на виду.

В GNOME панель открывается через **Ctrl+Alt+H**, если сочетание свободно. Нажатие на крестик рядом с задачей **убирает её из панели, но не останавливает процесс**. `Ctrl+Z` в окне HUD возвращает запись в текущем сеансе.

## Границы работы

Process HUD не управляет остановкой или перезапуском процессов и не гарантирует, что они переживут выход из системы или перезагрузку. Сбой связи сам по себе не считается ошибкой задачи. Для реального прогресса нужна информация от программы; проценты не вычисляются по загрузке процессора.

Проверены Linux/GNOME/X11, локальные задачи, подключение к Docker и автоматическое возобновление Codex через описанный мост, включая ошибки и прерывания. Реальные Kubernetes Job и удалённый запуск по SSH в опубликованном отчёте не значатся среди проведённых живых испытаний. Windows, macOS и полноценное поведение поверх окон в Wayland не проверены.
